Opening read-aloud (0–4)

Framing · Sinek · Why/What vs How · 80/20 target

›

Opening framing (read aloud first):

Today you’ll learn how to turn an engineering goal into a checked result with AI: define what matters, choose the tools and data boundaries, give it context, and delegate the work while keeping human review and accountability.

Verified Sinek excerpt (single source-linked quote; TED talk listed in Sources). Character count of quoted sentence: 53.

People don't buy what you do; they buy why you do it.
— Simon Sinek, How great leaders inspire action, TEDxPuget Sound, 2009

Speaker script, original paraphrase, not Sinek's wording: Sinek's point is that most companies explain themselves from the outside in. Here is what we make, here is how it is better, please buy it. His Apple illustration reverses the order. Apple leads with a belief, challenging the status quo and thinking differently, then explains how it acts on that belief with well-designed, easy-to-use products, and only then mentions what it sells: computers. Same products, different order, and the belief is what people respond to.

The flip: for most of engineering history the how consumed us. Syntax, boilerplate, wiring, test scaffolding. With agentic AI, much of the how can be delegated. Our job moves inward: why are we building this, what exactly should exist, and how will we know it is right. The AI proposes the how. We keep the acceptance criteria and the accountability.

Christian's working target is roughly 80% AI effort and 20% human effort, with the human 20% spent on strategy, risk, outcome review and exceptions. It is a goal for our workflow, not a measured or universal number. This class was prepared that way: the instructor set the why and the topics; AI drafted; the instructor reviewed and decides what ships.

Segment notes (facilitator)

4–32 talking points

›

4–9 Models, inference, local vs cloud

  1. Claude Code is agentic tooling: it reads files, runs commands, edits code and calls a model. It is not itself a model.
  2. Models differ in capability, speed, cost and context window. Route routine work to faster models, hard reasoning to stronger ones. Name families correctly: Opus, Sonnet and Haiku are Anthropic's Claude models; GPT models are OpenAI's.
  3. Inference is the model call. Prompt plus selected context goes to whichever backend is configured. A desktop app is an interface; unless you run open-weights models on your own hardware, inference happens in someone's cloud.

9–15 Backends, plan myths, Bedrock vs GovCloud

  1. Teachable correction: paying $200 rather than $20 for ChatGPT does not make inference stay off the provider. Both are consumer plans; OpenAI still processes every prompt. The training toggle exists on Free, Plus and Pro alike.
  2. Opting out of training is not the same as no provider processing, which is not data residency, which is not local or offline inference. Four different questions.
  3. Bedrock backend (CLAUDE_CODE_USE_BEDROCK=1): inference goes to Amazon Bedrock in the region you set, using your AWS credentials and IAM.
  4. Per Claude Code docs, Bedrock defaults turn off metrics, error reports and /feedback upload, but a session survey prompt and a WebFetch hostname check to Anthropic still run unless disabled (CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC, skipWebFetchPreflight).
  5. GovCloud regions use the us-gov. inference-profile prefix; model availability can lag commercial. GovCloud alone is not CUI, ITAR or CMMC compliance: authorization, approved models, settings, telemetry, networking and procedures all matter.

15–23 Harness and interfaces

  1. A harness is the loop around the model: tools, permissions, file access, memory files, hooks, stop conditions.
  2. New ways to talk to it: plain-language goals, CLAUDE.md, slash commands, skills, plan mode, voice.
  3. Same harness, different doors: terminal, VS Code extension, Claude Code Desktop. Use the comparison table; compare harness, context and permissions, not just model names.
  4. On VS Code: the owner's sense that it is losing ground is a hypothesis. Stack Overflow's 2026 survey still shows 70.9% regular use, the top IDE. What is changing is where the agent lives, not the editor's reach.

23–32 Context, planning, storage

  1. Walk the context menu below; ask the room which item they skip most.
  2. Planning stages: why and constraints, options, decision (ADR), plan, build, verify.
  3. Show the one-page ADR and the storage matrix for the running example.

Context menu

What to give the agent

›
  • The prompt — Goal, constraints, acceptance criteria
  • Project memory — CLAUDE.md conventions, commands, do and don't
  • Files and references — Point at specific files; the agent can read the repo
  • Decision records — ADRs explain why, so the agent doesn't relitigate
  • Structured data — JSON inputs and fixtures it can compute from
  • Tools and skills — What it may run and reusable procedures
  • Feedback — Test output, review comments, your corrections

Engineering demo kit (32–40)

Prompts · calculations · human exception

›

Instructor prompt 1, general form:

This is roughly what I'm trying to achieve: a small off-grid sensor station that runs year-round on solar and a battery. What public standards, engineering principles and rules of thumb should I consider? List the questions and assumptions you need from me before estimating.

Expected observation: the AI asks about load profile, sun hours, days of autonomy, battery chemistry and depth of discharge, temperature, and system losses. Nothing about the real project is revealed.

Instructor prompt 2, declared numbers:

Assume 5 W average load, 3 days of autonomy, 12 V battery usable to 50%, 3.5 peak sun hours, 70% overall system efficiency. Size the battery and panel, show units at every step, then do an independent order-of-magnitude check and tell me how many days a full recharge takes.

Prepared calculations:

Daily energy = 5 W × 24 h = 120 Wh/day

Battery = (120 × 3 Wh) / 0.5 = 720 Wh = 60 Ah at 12 V

Panel = 120 Wh / (3.5 h × 0.7) = 49 W → choose 60 W

Recharge = 360 Wh / (60 × 3.5 × 0.7 − 120 = 27 Wh/day) = 13.3 days

Sanity check: 60 W × 3.5 h × 0.7 = 147 Wh/day, above the 120 Wh load. 60 Ah × 12 V × 0.5 = 360 Wh, three days of load.

Human exception decision: The panel covers an average day but needs about 13 days to refill after a 3-day outage. Is that acceptable? The AI computed it; an engineer decides, perhaps a larger panel. Limitations: synthetic averages, no temperature derating, no seasonal sun data. A real design needs qualified engineering validation and the applicable codes.

Fallback if tools are slow: show the prepared calculation above and the expected question list.

Warning: Synthetic-only example. Do not execute against real repos, AWS accounts, messages, or controlled data without a separate explicit ask.

Crosswalk boundaries (40–44)

Coded labels are not declassification

›
Coded label (illustrative)Real item
=S1-G1Solar panel
=S1-G2Battery
=S1-K1Charge controller

Labels are IEC 81346-inspired for illustration only. The pattern: discuss generalized, coded problems outside; keep the mapping key in the approved secure environment.

Coding is not declassification: Coded names do not make controlled data shareable. If the payload itself is controlled, it stays inside the approved boundary regardless of labels, and anonymization never authorizes moving it out.

GitHub close-the-loop (44–53)

Worktrees · AI PR · human gate

›

Instructor prompt 3, run in a git worktree:

Create a branch, add inputs.json and a power-budget script with tests for the numbers we just checked, run the tests, open a pull request with a summary and the ADR link. Don't merge. When you think you're done, re-check: tests run, PR opened, description complete.
  1. Worktree per task — git worktree add ../station-budget -b feat/power-budget keeps parallel agents isolated
  2. AI implements — Code, tests, commit, PR description
  3. Remind to finish — Agents stop early; ask explicitly for tests, PR, and checks
  4. Human reviews — Strategy, outcome, exceptions; not every line
  5. Merge only when authorized — Required checks and branch protection pass; never bypass approvals

Demo uses a throwaway sandbox repo. Fallback: a prepared PR screenshot.
